# 系统架构

## 1. 架构目标

系统采用三段式架构：

- 前端 Web：普通用户填报入口和管理员后台。
- 服务端 API：表单校验、业务计算、查询统计、管理员认证。
- 数据库：保存上报记录、管理员配置和系统数据。

整体目标是先实现稳定可用的局域网缺考上报闭环，再逐步扩展权限、导出、报表和更复杂的统计能力。

## 2. 架构分层

```text
浏览器
  |
  | 局域网 HTTP 请求
  v
前端 Web
  |-- 普通用户填报页面
  |-- 管理员登录入口
  |-- 管理员后台页面
  |
  | API 请求
  v
服务端
  |-- 管理员密码验证
  |-- 表单数据校验
  |-- 缺考人数和出考率计算
  |-- 汇总统计
  |-- 历史数据查询
  |
  | 数据读写
  v
数据库
  |-- 上报记录
  |-- 管理员配置
  |-- 后续扩展数据
```

## 3. 前端设计

### 普通用户页面

职责：

- 展示缺考上报表单。
- 做基础输入校验。
- 提交数据到服务端。
- 展示提交结果。
- 页面底部提供管理员入口。

建议页面结构：

- 页面标题。
- 基本信息区域。
- 人数上报区域。
- 缺考名单和备注区域。
- 提交按钮。
- 底部管理员入口。

### 管理员后台

职责：

- 管理员密码登录。
- 展示汇总卡片或汇总区域。
- 展示上报明细列表。
- 支持日期筛选。
- 支持标题模糊搜索。
- 后续支持导出和记录管理。

建议页面结构：

- 顶部筛选栏：日期、搜索框、查询按钮。
- 汇总区域：记录数、应到总数、实到总数、缺考总数、总体出考率。
- 明细列表：标题、日期、教室、科目、应到、实到、缺考、出考率、填报人、提交时间。
- 详情弹窗或详情页：展示完整上报内容。

## 4. 服务端设计

服务端是业务可信层，所有关键计算与校验都放在服务端。

核心职责：

- 接收普通用户上报。
- 校验必填字段和人数逻辑。
- 自动计算缺考人数和出考率。
- 保存数据库。
- 验证管理员密码。
- 为后台提供列表、详情、汇总统计接口。

关键原则：

- 不信任前端传来的计算字段。
- 数据库保存的统计字段必须由服务端计算。
- 查询接口需要支持分页，避免历史数据过多后页面变慢。
- 管理员接口需要认证保护。

## 5. 数据库设计

第一版建议至少包含：

- `absence_reports`：缺考上报记录。
- `admin_settings` 或配置文件：管理员密码哈希等配置。

如果第一版采用轻量数据库，可使用 SQLite；如果预计多人高频访问或后续部署更正式，可使用 MySQL 或 PostgreSQL。

## 6. 管理员认证

第一版可以使用单一管理员密码：

- 管理员从底部入口进入登录页或弹窗。
- 服务端验证密码。
- 验证通过后发放会话 Cookie 或 Token。
- 后台 API 校验会话。

安全注意：

- 不在前端硬编码管理员密码。
- 服务端保存密码哈希，不保存明文密码。
- 后续可扩展为管理员账号体系。

## 7. 部署方式

第一阶段按局域网部署考虑：

- 服务端在一台局域网内电脑或服务器运行。
- 前端由服务端托管，或单独静态部署。
- 局域网用户通过 `http://服务器IP:端口` 访问。
- 数据库存放在服务端本机或局域网数据库服务。

后续可以扩展：

- HTTPS。
- 反向代理。
- Docker 部署。
- 定时备份数据库。
